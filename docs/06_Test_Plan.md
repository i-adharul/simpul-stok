## Testing strategy

The most important tests are the ones that prove the product's main claims (concurrency, atomicity, tenant isolation), and all of them use a real Postgres.

| Test                      | What it proves                                                       | How                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Stock concurrency         | Stock never goes negative and no stock is lost or duplicated         | Run 20 simultaneous transfers against a stock of 10 with `Promise.all`; check the number of successes, the final stock, and the number of history rows                                                                                                                                                                                                                                                                                     |
| Transfer atomicity        | A failure midway rolls everything back                               | Force an error after the source stock is decremented; make sure the source stock is unchanged                                                                                                                                                                                                                                                                                                                                              |
| Tenant isolation          | Tenant A cannot touch B's data                                       | Create two organizations; for every endpoint and action, try to read, update, and delete an ID belonging to B from A's session; expect 404                                                                                                                                                                                                                                                                                                 |
| Role access               | Roles and warehouses are enforced                                    | Role × action matrix; expect 403 for those not allowed                                                                                                                                                                                                                                                                                                                                                                                     |
| Webhook                   | Safe and idempotent                                                  | A wrong token is rejected; the same event sent twice is processed only once                                                                                                                                                                                                                                                                                                                                                                |
| Plan limits and downgrade | The effective limit locks usage while a downgrade invoice is Pending | With a Pending downgrade invoice to Starter, additions above the Starter limit are rejected with `PLAN_LIMIT_REACHED` and a reason message; after the invoice is Paid, Expired, Failed, or cancelled, the limit returns; an upgrade does not lock; choosing Starter while usage exceeds its limit is rejected                                                                                                                              |
| Billing cycle             | The anchor date and invoice kinds are correct                        | Billing day 31: 31 Jan, 28 Feb, 31 Mar, 30 Apr; day 15 does not shift; validity per kind (initial and plan change 7 days, regular renewal due date + 10 days, replacement renewal the later of due date + 10 days and created + 7 days); paying during READ_ONLY moves the billing day to the payment date and does not trigger a new invoice until 7 days before the new period ends; paying during GRACE does not change the billing day |
| 30-day trial              | The trial ends without data loss                                     | Sign-up creates a 30-day period; after it ends, GRACE, READ_ONLY, then SUSPENDED follow; in SUSPENDED the Owner is directed to Choose a plan; paying the initial invoice (Starter or Business) activates the account and the data stays intact                                                                                                                                                                                             |
| Main flows (e2e)          | The application works from a browser                                 | 2-3 Playwright scenarios: login, transfer, register an organization                                                                                                                                                                                                                                                                                                                                                                        |

Supporting practices: Docker Compose for the local Postgres, a separate database for tests, consistent seed data, and CI that runs typecheck, lint, and tests on every pull request. Write the concurrency test **before** writing the transfer code, and let it fail first so the problem is seen happening.

## Registering a new endpoint (tenant isolation)

Every route under `src/app/api` must be accounted for in the cross-tenant harness (`src/test/tenant-isolation/`). `inventory.test.ts` fails CI when a `route.ts` is in none of three places, or in more than one:

| Where                              | For                                                       | What it needs                                       |
| ---------------------------------- | --------------------------------------------------------- | --------------------------------------------------- |
| `TENANT_ENDPOINTS` (`registry.ts`) | A tenant route (uses `withTenantRoute`). The normal case. | One entry per HTTP method, see below                |
| `EXEMPT_ROUTES` (`exemptions.ts`)  | A tenant route that cannot be tested this way.            | A written reason                                    |
| `PUBLIC_ROUTES` (`exemptions.ts`)  | A route that is not tenant at all (login, health, `/me`). | A written reason; it must not use `withTenantRoute` |

A registry entry has a `kind`: `item` (an endpoint addressed by one row's ID), `list`, or `create`. Together with the permission (`action`, from `can.ts`) and the role list derived from it (`allowedRoles: rolesFor(action)`), a way to create a row for either organization (`createRow`), and a way to read it back (`readRow`), that is all the harness needs. For each entry it then runs, from organization A's session against organization B's data:

| Check                                                       | Expectation                                                                                                                                         |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| No session                                                  | 401                                                                                                                                                 |
| Platform admin                                              | 403                                                                                                                                                 |
| A role that may not perform the action                      | 403, checked before the existence of the row, even for B's ID                                                                                       |
| Read, update, delete with B's ID                            | 404, byte-identical to the response for an ID that does not exist; B's row is left untouched                                                        |
| List                                                        | Contains none of B's rows (and contains A's own)                                                                                                    |
| Cursor holding B's ID (`supportsCursor`)                    | Returns none of B's rows                                                                                                                            |
| `organizationId` in the body or query                       | Ignored or rejected (400); never creates or moves a row in B                                                                                        |
| Missing or malformed `Idempotency-Key` (`idempotent: true`) | 400 `VALIDATION_ERROR`; no row is created                                                                                                           |
| Same valid request twice with one key (`idempotent: true`)  | Same 2xx status and identical body; only the second carries `Idempotency-Replayed: true`; exactly one row created (or the row is not changed again) |

The harness is proven by `harness.selftest.test.ts`: a correctly scoped test-only route passes every check, and routes built with one deliberate flaw each (plain client instead of the tenant client, authorization after the lookup, trusting `organizationId` from the body, and so on) fail the matching check with the expected message. Stock writes get two more flaws: a route that ignores the `Idempotency-Key` header, and a route that declares `idempotent: true` but never calls `runIdempotent`.
