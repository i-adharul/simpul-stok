## Data model (17 entities)

Every business table carries `organizationId`. The global exceptions are Plan and WebhookEvent. A platform admin is a User with a special role and an empty `organizationId`.

Every entity also has `createdAt`, and entities that are not append-only tables also have `updatedAt`. Neither is repeated in the columns below unless a screen needs it (the created date is shown on S08 and S19).

Main relations: an Organization has many Users, Warehouses, and Products, and one Subscription. StockLevel links Warehouse and Product. StockMovement records every change to StockLevel. StockTransfer groups the TRANSFER_OUT and TRANSFER_IN movements. An Invoice belongs to a Subscription and points to the Plan that takes effect once it is paid. An Invitation is recorded together with its creator (User).

Diagram: see `ERD.png` (17 entities).

**How to read it.** An arrow points to the "many" side of a relation. `StockLevel` stores the current balance, and every change always writes one `StockMovement` row in the same transaction (BL11 to BL13), so the link between them is drawn dashed as a logical relation. `Plan` and `WebhookEvent` are deliberately outside the tenant because they have no `organizationId`. `WebhookEvent` connects to `Invoice` only through `externalId`, not through a foreign key.

**Tenant isolation rules**

1. Only the `organizationId` from the server session is trusted, never one from the body or the URL.
2. All data access goes through one helper (a Prisma client extension) that adds the `organizationId` filter automatically.
3. Every `findUnique` on an ID taken from the URL still checks which organization owns it, so a guessed ID belonging to another tenant returns 404.
4. Composite indexes on large tables (StockMovement, StockLevel) start with `organizationId`.
5. Bonus: Postgres Row-Level Security as a second layer in case application code forgets to filter.
