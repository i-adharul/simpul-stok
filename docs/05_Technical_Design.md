## Tech stack and the reasons

Selection principles: (1) commonly used in the industry, (2) one person can run it, (3) it does not hide the things whose understanding the project wants to prove, and (4) the AI assistant in use (Claude) knows the ecosystem well. **Important note: client state and Redis**

Most of the "state" in an inventory application is server data (stock, history, products), and it is managed by Server Components or TanStack Query, not by a global store. Filters and pagination fit in the URL, so they can be shared and reloaded. The only meaningful client state is the multi-item transfer draft on S11, and local React state is enough for it. Redux and Zustand are not used in this version; they only make sense when state must persist across pages or be used by many distant components.

Redis is not used either. Idempotency is guaranteed by a unique key in the database (BL14), the demo scale does not need a dashboard cache, and rate limiting is deferred to later development. Redis (for example Upstash) is an option if traffic grows, for rate limiting, caching, or queues. Record this decision in an ADR.

**Verify before building (external facts, not design decisions):** the free-tier limits of Neon and Vercel (including whether a daily cron is allowed), the maximum Xendit invoice duration (whether a 7-day validity and due date + 10 days are allowed), and the Xendit webhook payload format may change. Check their pricing pages and official documentation. If anything differs, adjust the numbers, not the design.

## Architecture and security decisions

The code is layered so it is easy to test and explain: a page or action calls a **service**, the service uses **tenant-scoped data access**, and only the last layer touches Prisma.

1. **Request context:** reads the cookie, verifies the session, checks the user and subscription status (BL23), and then produces `{ userId, organizationId, role, warehouseIds }`. Every layer below only receives this context.
2. **Service:** holds the business rules (transfer, adjustment, subscription). It knows nothing about HTTP or React.
3. **Tenant-scoped data access:** a Prisma client extension that injects the `organizationId` filter automatically.
4. **Route Handlers (REST)** are the only entry point for write actions, webhooks, and cron. Server Components may read through a service for list pages.

**Stock transfers without negative stock**

- A whole transfer runs in one `prisma.$transaction`.
- Decrementing stock uses an atomic conditional update (`updateMany` with `where quantity >= amount` and then `decrement`). If the number of affected rows is 0, the stock is insufficient and the transaction is aborted. This prevents two requests from decrementing the last stock at the same time without an explicit lock.
- The database constraint `CHECK quantity >= 0` is the last safety net.
- When updating several stock rows, sort them by (warehouseId, productId), the same as BL13, to avoid deadlocks when two transfers in opposite directions run at the same time.
- `idempotencyKey` is unique, so a repeated request does not create a second transfer.
- Understand the default Postgres transaction isolation level (Read Committed) and when `SELECT ... FOR UPDATE` through `$queryRaw` is needed.

**Payment webhook**

- Verify the token or signature before reading the body.
- Store a `WebhookEvent` with a unique key; if it already exists, reply 200 without processing again.
- The invoice and subscription updates run in one transaction.
- Do not trust the status in the webhook body alone for anything critical; the invoice status must be fetched again from the gateway API before activating the account (BL22).

**Baseline security that is required**

- Cookies are `httpOnly`, `secure`, `sameSite=lax`; passwords are hashed with `bcryptjs` (cost 12, which is why a password has a maximum of 72 characters).
- All input is validated with Zod on the server, not only in the form.
- Rate limiting for login and sign-up does not exist in this version (deferred to later development); it is documented as a limitation in the README.
- Secrets live only in environment variables, never in the repo.
- Error messages to the user do not leak a stack trace or the existence of another tenant's data (always 404, not 403, for another organization's data).
- Structured logs with a request ID to trace problems.

## Supplementary technical decisions

Technical gaps that have been closed. The decision column is final.

| Item                          | Why it matters                                 | Decision                                                                                                                                                     |
| ----------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| CSRF and security headers     | REST with cookies is vulnerable if not guarded | `sameSite=lax`, check the Origin header for write methods, security headers, no CORS opened                                                                  |
| API documentation             | REST must be demoable                          | `.http` files in the repo, one file per resource                                                                                                             |
| Environment and configuration | Prevents mistakes in production                | `.env.example`, env validation with Zod, separate databases for local, tests, and production, controlled production migrations                               |
| Observability                 | Tracing bugs                                   | Structured logs with a request ID; Sentry is not used in this version                                                                                        |
| Backup and retention          | Customer data                                  | Rely on Neon's built-in backups; business data is not permanently deleted (archived), except IdempotencyKey; the audit log and history are kept indefinitely |
